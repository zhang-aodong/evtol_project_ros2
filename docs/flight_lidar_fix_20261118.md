# 起飞与雷达扇形帧修复（2026-11-18）

## 日志与复现依据

用户原始运行日志为 `reports/console_manager_20261118_212001_c92688.jsonl`，
ROS 快照为 `data/console_runs/ros_20261118_212229_da13d4`。
Gateway 进入 `takeoff` 后未进入 `flying`；安全节点反复报告
`Waiting for complete navigation LiDAR sweep`、`LiDAR acquisition age exceeds budget`
和 `LiDAR stale`。日志没有执行 `mission_land` 的证据；最终 `stopped` 对应用户点击停止。
因此“起飞后落回地面”不能解释为航点程序主动执行了降落。

修复前以原用户航点、32 架障碍机、UE 可视窗口和预览进程复现，直接读取 UE
共享内存，两个异常时刻分别观察到：主雷达空帧，导航雷达仅约 17.28°、319 点。
这证明窄扇形来自源头，而非仅由 Foxglove 丢失显示造成。

## 实现

1. UE LiDAR 新增 `CompleteScanPerUpdate: true`。每次更新使用固定角度网格、固定
   射线预算，完成配置视场的一次快照。以前扫描角度采用仿真时钟增量，发布触发
   却采用墙钟；固定步长时钟追赶时，一次更新可能只覆盖很小扇区。
2. 共享内存 v1 的槽位预留字段 bit 0 表示完整扫描，布局与槽位大小保持兼容。
   被截断的载荷不得标记完整。写入 guard 和 latest_frame_id 使用 UE 原子操作与
   内存屏障，读端仍执行双 guard 校验。
3. 导航采集节点只发布带完整扫描标记的帧；旧插件、未启用新参数或截断帧会报错，
   不能通过降低安全条件解锁起飞。标准共享内存雷达采集也验证此标记。
4. 默认 `navigation_lidar.minimum_sweep_s` 改为 `0.0`，消费已经验证的单帧扫描。
   不再用两帧时间戳间隔推断完整性，避免明明收到完整帧却因缺少第二个位姿插值
   区间而反复停止。显式非零窗口仍支持按采集时刻位姿补偿合并。
5. 采集时间戳、20 Hz 配置、共享内存传输、失效停车、位姿对齐、动态避障与最终
   降落验证继续生效。没有重写时间戳、重复旧帧、关闭避障或放宽数据超时。
6. `/diagnostics` 中的 `/drone1/navigation_lidar` 增加 `scan_complete`、`point_count`
   和 `capture_interval_s`。UE 空扫描会记录传感器名、帧号、真实位置、姿态与射线数。
7. 对视觉语义误分产生的地面假行人增加几何校验：只有整片位于配置地面支撑高度
   以下、厚度不超过 5 cm 的平面小片会被拒绝。抬高的无人机表面、直立行人及原始
   全向雷达保护仍保留。实测假目标高度约 -0.193 m、厚度仅 0.00006 m，之前会被
   跟踪器解释为移动行人并反复扩大动态避障范围。
8. 起飞时支撑面处理不再限制在初始点周围的 2 m 圆柱内，避免一次有效侧移后，圆柱
   外的同一地面变成包围本机的“障碍墙”。同时在普通候选及紧急避让候选经过平滑后
   都施加非下降速度约束，不能向被排除的支撑面下方飞。高于支撑面的障碍仍参与
   路径与速度检查；正常航点下降和最终降落逻辑不受这一阶段约束影响。
9. 异步规划失败保留 `goal_obstructed` 等实际原因，避免全部显示成一直等待计算。

这是在当前车辆姿态下生成的仿真快照，不模拟一圈扫描内部的逐射线运动畸变。
没有命中表面不等于没有发射射线；天空、遮挡与超量程区域不会人为补点。

## 话题与 Foxglove

| 话题 | 用途 | 配置水平视场 |
| --- | --- | --- |
| `/drone1/lidar/points` | 原始主雷达、感知及录制 | 前方 180° |
| `/drone1/navigation/lidar/points` | 全向导航安全雷达 | 360°，垂直 ±90° |
| `/drone1/preview/lidar/points` | Foxglove 的节流主雷达预览 | 与主雷达相同，前方 180° |

完整扫描指覆盖该雷达的配置视场。主雷达的半圆形视场是配置行为，不能据此要求
它显示 360°。需要观察四周时在 Foxglove 3D 面板添加导航雷达话题。
预览目标上限为 5 Hz，不能用它判定原始雷达是否达到 20 Hz。
正常扫描覆盖下，场景表面与距离仍会使点数和返回点的角度范围改变。

## 启动与迁移

当前机器已应用源码修复并编译。关闭旧 UE/ROS 会话后，从已有控制台依次启动 UE、ROS。
如果控制台仍是更新前打开的旧进程，先在其终端按 Ctrl+C，再运行：

```powershell
.\scripts\start_console.ps1 -NoBrowser
```

继续使用控制台原有的 WebSocket 连接地址和参数配置；不要连接验收探针的临时端口。
用户 `config/console.local.json`、障碍机数量、航点与模型权重未被本次修改覆盖。

迁移到另一台 Win11 时复制完整匹配的 UE 工程和 ROS 工程，配置本机路径后执行：

```powershell
.\scripts\ue_sensor_support.ps1 -PluginDirectory '<UE工程>\Plugins\AirSim' -Apply
.\scripts\build_ue.ps1
.\scripts\build.ps1
```

不要只复制某个旧 DLL；`ue_support/manifest.json` 包含本次修改的源文件校验值。
手动运行 UE 时也必须使用更新后的 `airsim.navigation_2k.json`。
若出现 `Incomplete navigation LiDAR frame`，检查当前实际插件、编译结果与配置，
不要用取消完整性校验或增大超时来绕过。

仅在内存中启用执行、障碍机与新会话。它启动自己的 UE、ROS、预览进程，采集源端
标记、原始与预览 PointCloud2 的点数/角度/时间戳/摘要、速度指令和飞行状态，
退出时停止自己的进程并恢复原点文件。

```powershell
. .\scripts\activate.ps1
$env:PYTHONPATH="$PWD\.visualization_deps;$PWD\.algorithm_deps;$env:PYTHONPATH"
$env:ROS_DOMAIN_ID='223'
python .\tests\probe_flight_lidar.py --label local_check --seconds 70
```
