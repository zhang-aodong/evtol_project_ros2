# 航点连线与实际已走轨迹

独立只读节点 `evtol_targeting.trajectory_node` 订阅当前会话的 `/simulation/reference_origin` 和 `/drone1/state/odometry`，发布两个标准 `nav_msgs/msg/Path` 话题。它不连接 AirSim、不发布指令、不参与航点到达判定或避障。

| 话题 | 内容 | 发布方式 |
| --- | --- | --- |
| `/drone1/navigation/waypoint_path` | 按 `mission.waypoints_enu_m` 顺序连接的完整航点折线，包括已完成与尚未完成的航点 | 收到会话起点后发布；Reliable + Transient Local，缓存最新一条 |
| `/drone1/navigation/traveled_path` | 从节点开始观察本会话起，累计实际收到的无人机位置；包含起点、最新位置及升降高度 | 默认最高 2 Hz，有新状态时更新；Reliable + Transient Local |

两者均使用起点相对的 `map_enu`，X=东、Y=北、Z=上，单位米。航点折线只包含配置航点，不自动插入 `[0,0,0]`；若要显示地面到首个起飞航点的线段，可在航点配置中明确加入对应起点，但修改航点同时也会修改飞行任务。原 `/drone1/navigation/path` 继续表示避障规划生成的局部路径，可作为第三条参考线。

实际轨迹读取 `/state/odometry`：当前 `state.source: truth` 时为真值轨迹，将来切换 `fused` 后为融合定位输出的轨迹。轨迹点保留状态消息的原始时间戳与姿态。不将指令速度积分成轨迹、不用航点替代实际位置。当前飞行中途启动时，只能从启动后收到的状态开始累计，不能恢复未记录的历史航迹。

## 启动

更新后运行原来的 `scripts/start_experiment.ps1` 或 `scripts/start_targeting.ps1` 即自动启动轨迹节点。已有实验运行时，只需另外开一个终端：

```powershell
.\scripts\start_trajectory.ps1
# 如果实验使用另一个配置文件：
.\scripts\start_trajectory.ps1 -Config config\navigation_validation.yaml
```

不要重复启动；命名互斥量会拒绝同一 AirSim endpoint/vehicle 的第二个轨迹节点。之后完整重启实验前，先在独立轨迹节点终端按 Ctrl+C，避免与 launch 自动启动的节点冲突。本次调试的临时后台节点已退出，其记录见 `reports/trajectory_live_process.json`；正常使用由实验 launch 自动启动即可。

```powershell
. .\scripts\activate.ps1
ros2 topic info /drone1/navigation/waypoint_path -v
ros2 topic echo /drone1/navigation/waypoint_path --once --qos-durability transient_local --qos-reliability reliable
ros2 topic echo /drone1/navigation/traveled_path --once --qos-durability transient_local --qos-reliability reliable
```

## Foxglove / RViz2

更新桥接后启动 `scripts/start_visualization.ps1 -Viewer foxglove`，连接 `ws://127.0.0.1:8765`。若旧桥接正在运行，先关闭该桥接再重新启动，新增白名单才会生效。

在 Foxglove 添加 **3D** 面板，显示坐标系选 `map_enu`，启用上述两个话题；航点轨迹设蓝色，已走轨迹设绿色，显示样式选择连线。也可启用 `/navigation/path` 显示当前避障规划线。桥接会缓存最近一次完整 Path，稍后打开面板时仍能获取已发布轨迹。

RViz2 的 Fixed Frame 设为 `map_enu`，添加两个 **Path** 显示，分别选上述话题，Reliability 设 **Reliable**，Durability 设 **Transient Local**；Line Style 可选 Lines/Billboards，分别设置颜色。缩放到无人机初始点附近，注意与绝对 `map` 坐标区分。

两个 Path 使用相同坐标系可直接比较。避障时实际轨迹偏离航点直线是正常行为；轨迹可视化本身不承诺某个航点已经完成，应以 `/mission/status` 为准。

## 采样与资源上限

`config/targeting.yaml` 可配置：

```yaml
trajectory:
  publish_hz: 2.0
  min_distance_m: 0.05
  max_points: 20000
```

状态流仍按原频率接收；累计关键点默认相隔至少 5 cm，每次发布补入最新实际位置，静止时不不断向历史追加重复位置。达到点数上限后，对整段历史隔点简化，保留最初点和最新点，并增大采样距离，防止长时间运行内存与消息大小持续增长；不截掉整段历史的开头。发布最多约 `max_points + 1` 个点。此为可视化折线，精确高频轨迹应通过 Odometry 录包分析。

新会话会清空已走轨迹；检测到状态时间倒退时先清空两个显示，等待新的会话起点，不将两次仿真连成一条线。节点不会读取或修改 `data/session_origin.json`。

`scripts/record.ps1` 已加入两个 Path、ENU 状态与会话起点，配套 QoS 可在晚启动录包时接收到已缓存的航点路线。后台停飞控制与录制无关联。

## 验证记录

相关 Python 功能包已编译，79 项回归通过（`reports/trajectory_regression.err.log`）。新增测试检查三维航点顺序、原始状态时间戳和位置、重复/无效状态、限长简化、跨会话清空、ROS 晚订阅缓存、Foxglove 面板晚订阅重放，以及隔离域中真实 ROS 状态消息经轨迹节点流入 Foxglove 桥接的集成链路。

现场只读检查时实验已退出，没有状态或会话起点发布者，因此 `reports/trajectory_live.json` 的该次观测无数据，不能当成真实飞行轨迹验收。未为此重启 UE、解锁或改变飞行。启动实验后可运行 `python scripts/probe_trajectory.py --seconds 15` 检查两条路径，输出每条折线及其最新点与实际 Odometry 的一致性。
