# 多机起飞失败修复与验证（2026-11-14）

## 原因

原失败运行 `data/console_runs/ros_20261114_023706_6ee8da` 中，管理器在所有障碍机
就绪后才启动本机控制网关。Drone15 初始化失败使启动中断，触发场景降落清理，
因此表现为本机不起飞、已起飞的障碍机又降落。

在原始 32 架配置中实测确认：Drone15 的出生位置与静态模型 `airpiane3` 重叠，
未解锁便穿落并以约 8 m/s 下坠。AirSim 随后拒绝对正在运动的无人机执行 takeoff。
Drone17 也存在出生碰撞和异常运动。视觉模型当时已正常完成 GPU 推理。

修复初始化后又复现了多机长时间运动 RPC 挤占服务线程、本机控制请求超时的问题。
另外，UE 刚启动即建立 ENU 原点会记录到本机尚在下落的出生位置。

## 修改

- 障碍机增加 `actors.initialization` 配置及面板选项。旧配置缺少字段时运行时补为
  `first_waypoint`，不修改用户保存的原航点和数量。
- `first_waypoint`：仅在实验开始前将障碍机布设到其第一个 ENU 航点，清零运动状态、
  解锁并通过实际位置和速度反馈验证稳定。这是空中实验布设，不是从地面真实起飞。
  航线飞行期间不进行瞬移；碰撞没有被全局关闭。
- `ground`：保留出生点真实起飞模式。必须选择有地面支撑且不与建筑、静态飞机或
  其他飞机重叠的出生点；正在下落的出生状态会明确报错，不会跳过安全检查。
- 执行模式下，障碍机在首航点稳定悬停，收到本次会话本机 `flying` 状态后执行后续航线。
  观察模式不等待本机起飞。
- 障碍航线使用限速、限加速度的位置反馈速度控制，运动 RPC 时长 0.02 s，
  间隔约 0.08 s，替换长时间阻塞的 `moveToPosition`。
  到点需要满足位置容差（默认 0.5 m）和速度门限，不以 API 返回成功代替实际到点。
- 执行模式先等待视觉真正完成推理，再初始化障碍机和本机控制。
- 新会话建立原点前，等待本机速度低于 0.15 m/s、位置漂移小于 0.04 m 并持续稳定
  0.8 s；15 s 内仍不稳定则报告出生位置/碰撞问题。本机继续通过控制网关正常起飞。
- 面板日志提前显示启动失败根因及具体飞机，并每 3 s 报告障碍机就绪进度。
- 障碍机收尾最多 16 路并发降落，工作线程退出共用 4 s 等待预算，避免逐机累积长等待。
  普通关闭仍执行降落；紧急结束继续使用已有“强制结束”按钮。

## 使用

本机已编译安装 `evtol_scenario`、`evtol_console` 并更新 Foxglove 扩展。
如管理器仍为旧进程，应先结束旧管理器再启动：

```powershell
cd D:\ZAD_Files\evtol_files\evtol_project_ros2
.\scripts\start_console.ps1 -NoBrowser
```

1. 重新加载 Foxglove，连接管理器打印的 WebSocket 地址，打开 EVTOL Simulation Console。
2. 障碍机页面选择“首航点空中布设并悬停”，确认首航点位于可飞行空域，保存参数。
   若需要真实地面起飞，选择 `ground` 并先校验所有出生点。
3. 启动 UE，等待 AirSim 就绪；在运行设置中启用执行控制与障碍机，再启动 ROS 实验。
4. 日志应依次显示视觉就绪、障碍机就绪数量增长、本机 arming/takeoff/flying、释放障碍机航线。

只点击“启动 UE”不会自动启动 ROS 或起飞；未启用执行控制时为 SHADOW 观察模式。

换电脑后沿用项目环境配置并重新构建，无需修改或重新编译 UE 工程：

```powershell
. .\scripts\activate.ps1
colcon build --merge-install --executor sequential --packages-select evtol_scenario evtol_console
. .\install\local_setup.ps1
```
