# 三相机前向覆盖与预警验收

## 当前配置

新增正前相机 `front_center`，左右相机 `front_left` / `front_right` 偏航改为 −60° / +60°。三路均为 1152×1536、水平视场 70°、上仰 12°，无新增鱼眼投影。水平标称覆盖区间为 [−95°, −25°]、[−35°, +35°]、[+25°, +95°]，合计约 190°，相邻重叠约 10°，覆盖前向水平 180°。竖幅使垂直视场约 86°，兼顾爬升时上方目标和巡航时稍低的目标。

这里的 190° 仅指水平覆盖。三路相机的上下方仍有盲区，不能将水平覆盖当成完整半球覆盖。

`config/targeting.yaml` 保存相机名称、顺序、外参和模型路径；`src/evtol_simulation/config/airsim.navigation_2k.json` 同步更新，支持手动启动 UE。控制台每次启动会生成本次运行的 `airsim.json`。改变相机后必须重启 UE，再启动 ROS；只重启 ROS 无法改变 UE 中的相机。

当前使用上一轮已经训练的 YOLO26n 权重，重新导出三路固定 batch FP16 ONNX：`models/drone_detection_diverse_20261120_b3_1536.onnx`。原始竖幅图像经过保持比例的 letterbox 成为批量输入 `[3,3,1536,1536]`，框再映射回原图；置信度保持 0.30，强制 CUDA，不允许无提示退回 CPU。训练权重未改变，本次没有重新训练模型。相机通过共享内存获取，三路按同一采集时间戳配对；融合仍使用视觉框和实际雷达投影，不使用真值生成在线检测。推理上限 15 Hz，相机采集配置仍为 20 Hz。

配置导入迁移到版本 6，为原版本 5 的草稿设置尺寸 1152×1536 和推理上限 15 Hz；航点、障碍机、机器路径不改变，`console.local.json` 未直接覆盖。当前版本 6 的用户配置保留其显式参数。兼容了 AirSim 竖幅 `getProjectionMatrix` 的长轴矩阵约定，实际融合和 CameraInfo 仍按 UE4.27 SceneCapture 水平 FOV 计算像素焦距，没有删除标定校验，也没有要求修改或重编译 UE。

曾使用 1536×2048 图像，但进入1536方形模型前会缩小到1152×1536；当前直接采集这一有效尺寸，保持网络的有效目标像素数量，减少43.75%的渲染像素，降低高负载时的仿真间断。

常规避障仍使用融合结果，原始点云仅在 2 m 内用于应急避障，规划配置 2 Hz。2 m 保护范围下当前执行速度上限约 0.99 m/s。预警独立保持 10 m 完整前向半球。

当前 UE 源码已按无人机数量扩容 RPC 线程。本次曾试验缩短障碍机阻塞 RPC 时长，但未解决真值缺口，已撤回该修改；保留原来 80 ms 的反馈等待、20 ms 的速度指令、限加速度、真实位置闭环和航线。没有在实验飞行途中用瞬移替代障碍机运动。评估日志增加了缺失时刻前后的真实采样时间，便于定位采样与评估排队问题。

Foxglove 继续使用 `perception/surround/rgb/compressed` 与 `perception/surround/detections_preview/compressed`，图像按左、正前、右排列；桥接已放行新增 `perception/roi_lidar/front_center/points`。面板说明和扩展均已重新构建。

## 验收口径

两次独立真实 UE 会话，各运行 32 架障碍机，环绕本机布设，沿水平距离 20 m → 7 m 的径向航线往返。本机目标高度 10 m。主指标为每次真实目标进入 **完整 10 m 前向半球后 0.5 s 内实际产生融合预警** 的成功率；没有剔除盲区、遮挡、爬升期间迟警，没有扩大统计期限，也没有改变历史保留时间。目标真值仅进入独立评估。

第一组使用原全方向布局、8/12 m 两高度；第二组方位整体偏移 7°、改为 7/13 m 两高度。两组分别报告，不能通过挑选最好一帧或仅汇总通过的一组来宣称达标。有效评分覆盖另行列出，未达到 95% 的会话不会通过脚本验收。

| 会话 | 及时预警 / 已完成进入事件 | 及时预警率 | 预警帧检出率 | 预警帧精确率 | 有效评分覆盖 |
|---|---:|---:|---:|---:|---:|
| three_camera_render_baseline | 47/47 | 100.00% | 95.22% | 98.45% | 97.57% |
| three_camera_diagnostic_holdout | 58/59 | 98.31% | 94.27% | 98.91% | 96.89% |

两组事件合计 105/106，为 99.06%。各组是否分别达到 90%：True。首轮包含迟警和漏警，失败记录保留在对应报告中。

每组结束时另有1次进入事件尚在0.5秒判定窗口内（pending），未计入“已完成进入事件”；其状态保留在 JSON。预警帧指标由实际预警匹配统计计算，区别于融合定位帧指标，后者另存在 JSON 中。逐次及时预警率与逐帧检出率不能互相替代。

上一轮双相机全方向实验结果为 24/48=50%，保存在 `reports/perception_diverse_20261120_dual-front/result.json`。这是历史参照；本次运行负载和事件次数不同，不把它作为严格同时间、同状态的逐帧 A/B 对照。

这些结果支持所测试的水平来向和高度层场景达到要求；不能推导出所有俯仰角、任意遮挡和任意运动速度下都超过 90%。若需要覆盖半球顶端、底端，还需改变相机俯仰或增加其他观察策略。

三相机下 6 架交叉障碍机飞行回归：航线完成 `True`，起飞后碰撞 0 次，最长航点低速停留 6.8 s。这是测试场景结果，不保证任意不可通行环境都能持续前进。

| 会话 | 三路推理中位耗时 | 图像到融合输出中位延迟 |
|---|---:|---:|
| three_camera_render_baseline | 37.43 ms | 132.00 ms |
| three_camera_diagnostic_holdout | 38.64 ms | 111.00 ms |

三路相机增加了渲染与融合负载。首轮相机归档输出出现 readback 重排序超时，部分传感器实际频率也低于配置目标；完整原始诊断保留在汇总 JSON 的 `sensor_diagnostics`。及时预警验收通过不等于本轮所有传感器频率验收通过。归档重排序流和在线三相机检测使用不同读取链路，没有通过放大在线数据有效期掩盖延迟。

## 使用与复现

控制台管理器已恢复空闲，Foxglove 连接 `ws://127.0.0.1:8766`，本地控制台 `http://127.0.0.1:9040`。重新加载 Foxglove 以载入新扩展，然后通过面板先启动 UE、再启动 ROS。已有管理器时无需重复运行启动脚本。

在另一台已配置环境的 Windows 11 机器上，从工程根目录运行 `scripts/start_console.ps1 -NoBrowser`；它会显示本次桥接端口。相机参数和功能包没有新增本机绝对路径依赖，UE 和 Python 路径沿用 `config/machine.local.json` / 控制台配置。

停止正在运行的 UE 和 ROS 后，可分别复现两组实验：

```powershell
.\scripts\verify_three_camera.ps1 -Scenario baseline -Seconds 100
.\scripts\verify_three_camera.ps1 -Scenario holdout -Seconds 100
```

脚本会保留用户草稿与原点，使用独立测试航线，记录结果并清理自己启动的进程。报告写入带时间戳的新目录，`meets_90=false` 时返回失败。

三相机模型重新导出方法（在模型 Python 环境中运行）：

```powershell
python .\scripts\export_detection_onnx.py --root . --weights models/drone_detection_diverse_20261120.pt --output models/drone_detection_diverse_20261120_b3_1536.onnx --batch 3
python .\scripts\check_detection_onnx.py --root . --batch 3
```

固定 ONNX batch 必须与相机数量相同。检查脚本的合成输入仅验证执行和维度，不用于声称检测准确率。

原始与汇总证据：`reports/three_camera_acceptance.json`、各会话 `result.json` / `telemetry.json`、运行快照和日志。相关回归共 150 项通过；另有 TypeScript 检查、Foxglove UI 测试和实际 CUDA 推理检查。

此前失败与诊断会话完整保留：`perception_three_camera_20261120_holdout`（方形相机上方迟警，85.71%）；`perception_three_camera_portrait_holdout`（启动时投影元数据校验失败）；`perception_three_camera_portrait_holdout_fixed`（95.83%及时预警，但有效评分94.49%，未通过）；`perception_three_camera_balanced_holdout`（93.75%及时预警，但有效评分92.82%，未通过）。不能用其中的高预警数字代替完整验收通过。

减小渲染尺寸后的初次变方位实验也保留：`perception_three_camera_render_holdout`（48/48及时预警，有效评分94.14%，未通过）。随后曾尝试缩短障碍机 RPC 指令时长，`perception_three_camera_final_holdout` 的评分覆盖仍为94.14%，因此已撤回该改动。表格中的基准及最终变方位复测均使用原有障碍机控制时序；后者仅增加只读真值缺口诊断。最终复测通过并不表示高负载下的评分间断已被彻底消除，应同时监控有效评分覆盖率；前述未通过会话均未删除。
