# 双路 2K、双雷达与 IMU 频率修复（2026-11-10）

本记录对应 `airsim.navigation_2k.json` 与 `simulation.perception_2k.yaml`，包含前向雷达、全向导航雷达、完整目标定位/避障算法栈和 Foxglove 预览/桥接。测试控制网关为 shadow，不解锁、不起飞、不启动场景 Actor。飞行性能与多障碍机负载须单独验证。

## 原因与实际修改

1. 基线仿真时间比例约 0.515。固定步长物理线程原来在每次耗时回调后重新相对等待，丢掉的物理步不会补回。现在仅对 SteppableClock 使用持续截止时间，短时超时后执行真实固定步长积分；暂停/恢复和超过 250 ms 的长停顿重新建立截止时间。未放大物理步长、修改源时间戳或增加 ClockSpeed。
2. 雷达每条射线原来复制参数、组合三个四元数、重复查询同一 Actor 的网格与身份。现在每帧组合传感器姿态、复用水平三角函数，并在一帧内缓存命中对象的语义信息。射线角网格、FOV、点数设置、距离、命中检测和点序保持原定义。
3. Python/OpenCV 的精确语义调色板转换，在本机 2048×1536 零图微基准下约 15.46 ms/帧。新增 `evtol_sensor_native`，通过 C ABI 对完整 BGR 三通道做精确查表，相同基准约 2.56 ms/帧；不把混合颜色误识别为合法类别。不依赖 Python 原生扩展 ABI，也不引入 torch。DLL 由 colcon 编译并安装，Python 查找当前 ament 前缀。真实场景的最终频率以完整订阅验收为准。
4. Windows 高频线程改用高精度 waitable timer，关闭进程自身的计时精度与执行速度节能限制。IMU 使用 Above Normal，不使用 Realtime 优先级或 CPU 绑核。
5. RPC `getImuData` 只返回最新值，在物理循环赶上进度时会漏掉真实生成的连续样本。新增 `UnrealImuSensor`，继承原 `ImuSimple`，在原噪声/动力学输出后写入 `AirSimImu_<vehicle>_<sensor>`。1024 个 128 字节槽保留每次原生更新，带版本、帧号和原子 seqlock。ROS 按 100 Hz 从真实历史抽取样本，不插值、不复用、不重写时间戳。
6. IMU 默认保留 100 ms 仿真时间缓冲，覆盖物理线程的短暂调度抖动。启动相位和系统调度还会增加额外年龄，最终窗口诊断快照约 156 ms；消息中的采集时间仍是真实采集时间。诊断 `imu_buffered_sim_age_s` 显示当前缓冲年龄，过载积压和环覆盖明确报错。已有 RPC 适配器保留，可设 `imu.transport: rpc` 对比，但该模式可能重新出现 latest-only 丢样。本版不宣称 IMU 端到端低于 30 ms。
7. ROS/DDS 继续使用 UDP 绕开已经定位的 Fast DDS SHM 原生崩溃，增加发送/接收缓冲并使用异步发布。UE 图像、雷达和新增 IMU 环仍然使用 Windows 共享内存，两层传输不混淆。
8. 验收使用独立 core/RGB/semantic/labels/IMU 进程，避免大图像检查阻塞同一 Python 观察者。IMU 观察者使用与高频采集相同的 Windows 调度设置，单流使用 SingleThreadedExecutor。原始频率、最大间隔、数据质量、同步及非空阈值均未放宽。导航雷达也加入独立消息布局与范围检查。

## 数据通路

| 数据 | UE 到 ROS 采集进程 | 目标频率 |
| --- | --- | --- |
| RGB / UE 语义彩色 / 类别 ID / 两路 CameraInfo | 双路 2048×1536 BGR8 主动共享内存；类别转换由采集节点完成 | 20 Hz |
| 前向 LiDAR | `AirSimLidar_Lidar1` 共享内存 | 20 Hz |
| 全向导航 LiDAR | `AirSimLidar_NavigationLidar` 共享内存 | 20 Hz |
| IMU | `AirSimImu_Drone1_Imu1` 原生样本历史共享内存 | 100 Hz |
| GPS、真值、时钟 | AirSim RPC | 10 / 20 / 20 Hz |
| GNSS 原始观测、5G-A | RPC 真值与原工程随机模型；真实 LOS 异步查询缓存 | 10 Hz |

GNSS 原始观测和 5G-A 为明确标记的 synthetic 仿真观测；5G 的 LOS 射线快照沿用原配置刷新周期，不代表每个 10 Hz 观测都重新做了射线查询。模型推理输出是另一条算法话题，不能将其频率与传感器发布频率混用。

## 编译、启动与迁移

所有命令从本 ROS 工程根目录执行。当前机已经构建 UE 插件与 ROS 包。换机时复制完整匹配的 UE4.27 工程及本 ROS 源码，填写 `config/machine.local.json`，安装工具链和锁定依赖环境，再执行：

```powershell
# 先关闭此 UE 项目及 ROS 采集/可视化节点。
.\scripts\ue_sensor_support.ps1 -PluginDirectory 'E:\UEProjects\MyProject\Plugins\AirSim' -Apply
.\scripts\build_ue.ps1 -Target MyProjectEditor
.\scripts\ue_sensor_support.ps1 -PluginDirectory 'E:\UEProjects\MyProject\Plugins\AirSim'
.\scripts\build.ps1
```

`build_ue.ps1` 从本机配置或 `-Editor/-Project` 参数查找 UE，不写死原机盘符；项目名带空格时显式传入 `.Target.cs` 中的 Target 名。`ue_support/manifest.json` 同时覆盖相机、雷达、IMU、物理时钟及传感器工厂源码。`-Apply` 会备份受影响文件；这些文件只适用于匹配的 UE4.27/CosysAirSim 基础版本。

```powershell
.\scripts\start_ue.ps1
# 等待 AirSim 就绪。另开终端：
. .\scripts\activate.ps1
ros2 run evtol_simulation preflight --config src\evtol_simulation\config\simulation.perception_2k.yaml
.\scripts\start_experiment.ps1
# 另开终端：
.\scripts\start_visualization.ps1 -Viewer foxglove
# Foxglove 连接 ws://127.0.0.1:8765。
```

`start_experiment.ps1` 默认 shadow，实际飞行仍需原来的 `-Execute`，并根据是否重建起点使用 `-NewSession`。本次频率修复不修改航点或解除安全条件。

```powershell
# 在发布节点持续运行时执行；测试期间不要停止发布者。
. .\scripts\activate.ps1
python scripts\probe_pipeline.py --duration 10 --output reports\my_pipeline.json
python scripts\validate_live.py --config src\evtol_simulation\config\simulation.perception_2k.yaml --duration 60 --warmup 10 --output reports\my_acceptance.json
```

若只测试单雷达仿真，使用对应 `simulation.source_2k.yaml`；`simulation.perception_2k.yaml` 额外要求实验栈发布导航雷达。修改 `config/targeting.yaml` 中的导航雷达频率/范围后，同步修改该仿真验收配置中的 `navigation_lidar` 契约。

`scripts/probe_foxglove.ps1` 使用当前 Foxglove SDK WebSocket 协议订阅预览、状态和 TF，可验证实际编码与传输负载；它不是屏幕渲染验收，也不会发布飞行指令。

## 验收口径与证据

最低平均接收频率为目标的 97.5%，最高为 110%；RTF 要求 0.95–1.05；采集与墙钟最大间隔均不超过 4 周期；RGB/语义原始采集戳精确配对率至少 95%，相机/前向雷达最大差 50 ms。前向雷达要求没有空帧，消息布局、数值、frame、TF 和发布诊断也必须通过。`frequency_passed` 只代表平均频率，不能替代完整 `passed`。

基线 [frequency_baseline_20261110.json](../reports/frequency_baseline_20261110.json) 中 RGB 约 16.87 Hz、语义约 15.08 Hz、IMU 约 88.87 Hz、RTF 约 0.515。修复阶段所有 FAIL 报告保留用于诊断，不能把早期只有平均频率达标的结果当成完整验收。部分试验因发布窗口先于观察窗口结束而数据不足，也不属于有效的完整性能窗口。

Foxglove 客户端实际接收记录见 [frequency_release_foxglove.json](../reports/frequency_release_foxglove.json)；此客户端覆盖完整严格验收窗口。前一轮 180 秒测试记录 [frequency_foxglove_client.json](../reports/frequency_foxglove_client.json) 收到 RGB、语义、点云、模型语义预览、状态和 TF，共约 151.6 MB。原始 2K 话题以完整分辨率验收，Foxglove 仅订阅单独的预览派生话题。

全栈稳定性记录见 [frequency_release_shadow.json](../reports/frequency_release_shadow.json)。模型语义推理输出约 18–19 Hz，属于算法处理结果；UE 语义传感器与类别图的 20 Hz 验收不能用来宣称模型推理也严格达到 20 Hz。

独立 C++ 回归已验证：100 m 射线终点与原四元数实现的最大差约 0.0000684 m；固定步长在带周期性 20 ms 阻塞的 2 秒测试中由原 442 步恢复至约 663 步（理想约 667），暂停后不会补做暂停期间的物理步。测试源位于 `tests/test_lidar_ray_geometry.cpp`、`tests/test_fixed_step_scheduler.cpp`，几何测试编译时添加匹配 AirLib/include 与 AirLib/deps/eigen3 include 路径。

最终 Python 回归共 **70 项通过**，覆盖精确颜色转换与非连续数组、IMU 环空历史/乱序时钟/覆盖/撕裂保护、原始样本抽取、导航点云独立格式/范围、ROS 数据契约以及原有定位/规划/安全控制。日志为 `reports/frequency_unit.err.log`。UE 与全部 ROS 功能包已重新构建，`ue_sensor_support.ps1` 源码哈希检查、PowerShell 与 DDS XML 解析均通过。

本机窗口结果不代表另一台 Windows 11 的性能保证，也不构成硬实时调度保证；换机后仍应在实际图像、场景、模型、可视化和录包负载下运行同一验收。MCAP 同时录制的磁盘负载与飞行/Actor 负载未包含在当前静止 shadow 测试中。
